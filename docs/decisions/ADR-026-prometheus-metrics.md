# ADR-026 — Prometheus Exposition Format for Metrics

## Status
Accepted

## Decision
Every FrontWatch service (`ingestion`, `worker`, `control-api`, and the `alert-evaluator` poll loop) exposes a `GET /metrics` endpoint in Prometheus's plain-text exposition format, alongside `GET /health/live` and `GET /health/ready`. Go services use the official `github.com/prometheus/client_golang` (v1.24.1) client; TypeScript services use `prom-client` (v15.1.3, pure JS, no native bindings — confirmed Bun-compatible via its own `package.json`: no peer dependencies, its only runtime dependencies — `@opentelemetry/api`, `tdigest` — are pure JS too).

## Context
`observability.md` and `operations.md` (data-plane) both require this layer to be real, not aspirational: *"FrontWatch observes FrontWatch's own health"* is called out as **mandatory, not optional** (`charter.md` Principle 6). `operations.md` names the specific signals: *"Core metrics per service: requests, errors, latency, queue depth, worker throughput, database latency, telemetry ingestion."* Step 5's own PROGRESS.md deferral already flagged `/health/live`/`/health/ready` and ingestion metrics explicitly as "Step 8's job" — this ADR is that job.

No metrics format or library was specified anywhere in the docs. Prometheus's text exposition format was chosen over the alternatives (StatsD/DogStatsD push, OpenTelemetry Metrics SDK, a hand-rolled JSON endpoint) because:

- It's the de facto standard for exactly this shape of system (pull-based scraping of counters/histograms/gauges from a small fleet of long-running services) and every major self-hosted monitoring stack (Prometheus itself, Grafana Agent, VictoriaMetrics, Datadog's OpenMetrics integration) speaks it natively — important since FrontWatch is explicitly a self-hosted product (`deployment-models`, `infrastructure.md`) whose customers bring their own monitoring stack rather than FrontWatch mandating one.
- It's pull-based, which matches "expose `/metrics`, let the operator's own Prometheus/Grafana stack scrape it" better than a push-based system that would require FrontWatch to know its operator's ingest endpoint and credentials — extra configuration surface a self-hosted product shouldn't need just to be observable.
- `go.mod` already has no metrics dependency at all (a genuinely open choice); `client_golang` is the reference implementation the format's own spec is written against.
- OpenTelemetry Metrics was considered and rejected for this slice: it solves a superset problem (metrics + traces + logs, multiple possible backends) this project doesn't need yet — `operations.md` does call for **tracing** across `Ingestion → Queue → Worker → ClickHouse` too, but that's real, separate, not-yet-built work (tracked as deferred below), not a reason to adopt OTel's heavier metrics API today just to keep the door open.

## Rationale
Every metric name follows Prometheus naming convention (`<service>_<noun>_<unit>_total` for counters, `_seconds` for durations) and **never carries a high-cardinality label** — `operations.md`'s explicit caution ("never create metric labels from arbitrary high-cardinality values... user ID, session ID, full URL, error message") is enforced by construction: HTTP request metrics label by *route pattern* (e.g. `/api/v1/projects/:projectId/issues`, Elysia's own route definition string) and method/status, never the resolved path or query string.

`/health/live` and `/health/ready` are deliberately different checks, not aliases of each other (`operations.md`'s graceful-shutdown section implies the same distinction other cloud-native services make): liveness means "the process is up and its own event loop/goroutines are running," answered without touching any dependency — a slow Postgres must never make a service look dead and get killed by an orchestrator's liveness probe. Readiness means "this service's actual dependencies are reachable" (Postgres/ClickHouse/Redpanda, whichever a given service needs) and is what should gate traffic/rollout.

## Consequence
Every service in this monorepo gains the same three endpoints with the same meaning, so an operator (or FrontWatch's own future internal dashboard) can treat them uniformly. The specific metrics shipped in this slice are the ones `operations.md` names explicitly (requests/errors/latency per service, events accepted/rejected for ingestion, records processed/failed for the worker, evaluation cycles/notifications for the alert-evaluator) — not an exhaustive instrumentation pass over every function in the codebase. Deferred, not forgotten: per-query-function database latency (this slice covers HTTP-request-level latency and the two readiness pings, not a timing wrapper around every `db/*.ts` query — a much larger retrofit), distributed tracing across the ingestion→queue→worker→ClickHouse path, consumer-lag/queue-depth (needs a Kafka admin-client call `franz-go` doesn't do for free, a real separate piece of work), and any actual dashboard/alerting *on* these metrics (`observability.md`'s SLIs/SLOs/anomaly-detection/on-call apparatus — this ADR covers exposing the raw signals, not the operational program built on top of them).

**Real bug found and fixed while building the TypeScript side**: `control-api` and the `alert-evaluator` are separate real OS processes in production (ADR-025), so each calling `prom-client`'s `collectDefaultMetrics()` against the library's shared *global default* registry seemed harmless — until `bun test` loaded both modules into one shared process in the same run and the second `collectDefaultMetrics()` call threw `"A metric with the name process_cpu_user_seconds_total has already been registered"`, which cascaded into ~136 unrelated test failures across the whole suite (one throwing top-level module import poisons every file sharing that process). Fixed by giving each TypeScript service its own dedicated `new client.Registry()` instead of the shared default — genuinely correct either way (each service's metrics were always conceptually independent), not just a test-only workaround; the Go side never had this risk since each Go service is always its own separate binary/process, with no equivalent "both modules loaded into one test process" scenario.
